# ADR-089: Calcular o último código de cada tipo a partir dos resíduos do banco

- **Status:** Aceita
- **Data:** 2026-11-28
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

Pelo ADR-032, o `GerarCodigoResiduo` guardava só o último código gerado, de qualquer tipo, no
arquivo `arquivos/codigo.json`. Com o banco (ADR-085), esse era o último arquivo que o
sistema ainda precisava para funcionar. Manter um arquivo só para isso traria de volta o
problema de dois lugares com dados: se o banco fosse recriado ou outra pessoa rodasse em outro
computador, o `codigo.json` e os resíduos do banco poderiam não bater, e o sistema geraria um
código que já existe.

A informação, na verdade, já está no banco: cada resíduo salvo tem o seu código.

## Decisão

> Vamos calcular, ao iniciar, o maior código de cada tipo a partir dos resíduos que vêm do
> banco, e apagar o `codigo.json`, porque assim o banco é a única fonte e o código nunca se
> repete com um resíduo existente.

- O `GerenciarResiduosService` cria o gerador passando os resíduos que o repository carregou:
  `new GerarCodigoResiduo(gerarResiduosRepository.listar())`.
- O construtor percorre a lista e guarda, num `EnumMap<TipoResiduo, Integer>`, o maior código
  de cada tipo (`merge` com `Math::max`).
- O próximo código continua com a mesma conta, mas agora a partir do último **do mesmo tipo**:

```text
candidato = último do tipo + 1
distância = (resto do tipo − candidato) mod 5
próximo   = candidato + distância
```

- O código continua com 6 dígitos (`%06d`) e `código mod 5` continua indicando a categoria
  (ADR-004).
- Depois de gerar, o mapa é atualizado em memória. Não há mais nada para gravar.

## Alternativas consideradas

### Alternativa 1: Manter o `codigo.json`

- **Prós:** nenhuma mudança.
- **Contras:** um arquivo fora do banco que pode ficar diferente dele.
- **Por que não foi escolhida:** vai contra o ADR-065 (dados só no banco).

### Alternativa 2: Perguntar ao banco com `SELECT MAX(codigo)` a cada cadastro

- **Prós:** sempre o valor mais novo, até se outra pessoa cadastrou ao mesmo tempo.
- **Contras:** uma consulta a mais em cada cadastro, e o `GerarCodigoResiduo` passaria a
  depender do banco.
- **Por que não foi escolhida:** os resíduos já estão em memória. Calcular uma vez no início
  basta para o programa de terminal.

### Alternativa 3: Continuar com o último de qualquer tipo (ADR-032)

- **Prós:** o código também mostraria a ordem geral de cadastro.
- **Contras:** depois de olhar todos os resíduos, saber o último de cada tipo é tão fácil
  quanto saber o último geral, e por tipo o código cresce mais devagar.
- **Por que não foi escolhida:** o grupo preferiu a sequência por tipo, e os códigos de tipos
  diferentes nunca batem porque o resto da divisão por 5 é diferente.

## Consequências

### Positivas

- Um arquivo a menos, e o banco como única fonte.
- Recriar o banco ou trocar de computador não gera código repetido.

### Negativas

- O código deixa de mostrar a ordem geral de cadastro entre tipos diferentes.
- Se o resíduo com o maior código de um tipo for excluído, o próximo cadastro daquele tipo
  reaproveita o código dele, porque o maior passa a ser o anterior. O resíduo antigo não existe
  mais, então não há conflito, mas um registro do log que cite aquele código pode confundir.
- Com o servidor web e várias pessoas cadastrando ao mesmo tempo, o mapa em memória pode
  gerar o mesmo código duas vezes se não houver sincronização.

### Neutras

- A constante `CODIGO_PATH` ainda está na `Constantes`, mas não é usada.

## Riscos e pendências

- [ ] Tirar o `CODIGO_PATH` da `Constantes`.
- [ ] Atualizar o README na parte do código do resíduo (agora é por tipo, sem `codigo.json`).
- [ ] No Spring, deixar o `gerarCodigo` `synchronized` ou garantir `UNIQUE` no `codigo` do banco.
