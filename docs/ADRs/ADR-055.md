# ADR-055: Terminar o back-end em Java puro e fazer o front-end depois, com Spring Boot e Thymeleaf

- **Status:** Aceita
- **Data:** 2026-11-23
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

O projeto já tinha o Spring Boot no `pom.xml` (ADR-038) e um front-end em HTML, CSS e
JavaScript puros (ADR-041), mas os formulários ainda não conversavam com o back-end. Com o
projeto integrador, o back-end ganhou muita coisa nova (solicitações, fila, log, cargos,
grafo), e o grupo ainda está estudando o Spring. Mexer no back e no front ao mesmo tempo
multiplicaria os pontos de erro, como já tinha acontecido com o banco (ADR-042).

## Decisão

> Vamos terminar primeiro o back-end em Java puro e, depois, fazer o front-end com Spring Boot
> e Thymeleaf, com as páginas montadas pelo servidor.

**Ordem**

| Etapa | O que entra |
| --- | --- |
| 1. Back-end em Java puro | Domínio, services, repositories, estruturas e regras, testados sem servidor |
| 2. Spring Boot + Thymeleaf | Controllers que chamam os mesmos services e devolvem páginas HTML prontas |

- Nesta etapa não existe tela de terminal nova: as regras são testadas direto pelos services.
  O front bonito vem na etapa 2.
- O **Thymeleaf** monta o HTML no servidor, já com os dados. O controller chama o service e
  entrega o resultado para a página, sem precisar de `fetch` nem de JSON no JavaScript.

## Alternativas consideradas

### Alternativa 1: Continuar com o front em HTML, CSS e JS puros chamando o back por HTTP (ADR-041)

- **Prós:** front e back separados; o front já tinha telas prontas.
- **Contras:** exige controllers REST, JSON e `fetch` em cada formulário, e a conversão dos
  valores do front para os enums (tabela do ADR-041).
- **Por que não foi escolhida:** com Thymeleaf, o grupo escreve menos código de ligação e
  aproveita o que estuda de Spring.

### Alternativa 2: Fazer back e front ao mesmo tempo

- **Prós:** o app ficaria visível mais cedo.
- **Contras:** mudanças no back quebrariam o front a cada passo.
- **Por que não foi escolhida:** primeiro estabilizar as regras, depois a interface.

## Consequências

### Positivas

- As regras ficam prontas e testadas antes da interface.
- Os services não mudam quando o Spring entrar: o controller só ocupa o lugar da tela.

### Negativas

- O app só fica bonito e navegável perto do fim do prazo.
- As páginas do ADR-041 precisam ser adaptadas para templates do Thymeleaf.

### Neutras

- O Spring continua no `pom.xml` enquanto isso (ADR-058).

## Riscos e pendências

- [ ] Reservar tempo suficiente para o front antes da entrega de 05/12/2026.
- [ ] Mover as páginas para `src/main/resources/templates/` quando o Thymeleaf entrar.
