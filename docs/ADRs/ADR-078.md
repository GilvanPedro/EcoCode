# ADR-078: Usar a ArvoreAVL genérica como índice dos resíduos, com o código como chave

- **Status:** Aceita
- **Data:** 2026-11-26
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

O ADR-049 decidiu usar uma árvore AVL em memória como índice das buscas. Os resíduos ainda
estavam num `LinkedHashMap` (ADR-036). Faltava implementar a árvore e escolher onde usá-la
primeiro. O resíduo é buscado pelo código o tempo todo (editar, excluir, solicitar), então
ele era o candidato natural.

## Decisão

> Vamos implementar a `ArvoreAVL<K, V>` e o `NoAVL<K, V>` no pacote `Estrutura` e usar a árvore
> no lugar do `Map` do `GerenciarResiduosRepository`, com o código do resíduo como chave,
> porque a busca por código é a mais usada e a AVL garante O(log n).

| Classe | Papel |
| --- | --- |
| `NoAVL<K, V>` | Chave, valor, filho esquerdo, filho direito e altura; nasce com altura 1 |
| `ArvoreAVL<K extends Comparable<K>, V>` | `inserir`, `buscar`, `remover`, `contem`, `emOrdem`, `altura`, `tamanho`, `estaVazia` |

- Depois de cada inserção ou remoção, `balancear` olha o fator (altura da esquerda menos a da
  direita) e faz as rotações dos quatro casos: esquerda-esquerda, esquerda-direita,
  direita-direita e direita-esquerda.
- Inserir uma chave que já existe só troca o valor. Isso é usado no `editar` do repository.
- Na remoção de um nó com dois filhos, ele recebe a chave e o valor do sucessor (o menor da
  subárvore direita), e o sucessor é removido.
- `listar()` do repository devolve `emOrdem()`, ou seja, os resíduos ordenados pelo código.
- Ao iniciar, o repository lê o JSON e insere cada resíduo na árvore.

## Alternativas consideradas

### Alternativa 1: Continuar com o `LinkedHashMap`

- **Prós:** busca O(1) em média e mantém a ordem de cadastro.
- **Contras:** não mostra nenhuma estrutura estudada na disciplina.
- **Por que não foi escolhida:** o projeto integrador pede estruturas implementadas pelo
  grupo (ADR-049).

### Alternativa 2: Árvore binária de busca sem balanceamento

- **Prós:** bem mais simples.
- **Contras:** os códigos são gerados em ordem crescente (ADR-032), o que transformaria a
  árvore numa lista, com busca O(n).
- **Por que não foi escolhida:** é justamente o caso em que o balanceamento faz diferença.

## Consequências

### Positivas

- Busca, inserção e remoção por código em O(log n), mesmo com códigos em sequência.
- A listagem já sai ordenada pelo código, sem ordenar depois.

### Negativas

- A **ordem de cadastro deixa de existir** na listagem. A tela ainda pergunta "1 = cadastro,
  2 = código", mas as duas opções agora mostram por código.
- A busca por `id` (`buscarPorId` no service) percorre a lista inteira, O(n), porque a
  chave da árvore é o código.
- Hoje a árvore é atualizada antes de gravar o arquivo; o ADR-049 pedia gravar primeiro e só
  depois mexer na árvore.

### Neutras

- `buscar` com chave nula lança `NullPointerException`; o service sempre valida o código antes.

## Riscos e pendências

- [ ] Tirar a pergunta de ordem da tela de listagem, ou guardar a data de cadastro no
  resíduo para ordenar por ela.
- [ ] Quando o banco entrar (ADR-065), inverter a ordem: gravar no banco e só depois inserir
  na árvore, como pede o ADR-049.
- [ ] Avaliar uma segunda árvore com o `id` como chave, se a busca por id ficar lenta.

## Referências

- Substitui o ADR-036 (ordem de cadastro com `LinkedHashMap`).
- ADR-049 (AVL como índice), ADR-032 (códigos em sequência), ADR-071 (status do resíduo).
