# ADR-071: Dar um status ao resíduo e só aceitar solicitação de resíduo disponível

- **Status:** Aceita
- **Data:** 2026-11-25
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

Hoje nada impede o usuário de pedir a retirada do mesmo resíduo duas vezes. Ele cria uma
solicitação para o notebook velho, esquece, e cria outra. A fila passa a ter dois pedidos para
o mesmo objeto, o funcionário pode sair duas vezes para buscar a mesma coisa, e o histórico
fica confuso.

O ADR-051 definiu os quatro status da solicitação (Pendente, Em rota, Concluída e Cancelada) e
o ADR-064 colocou as solicitações num repository por id, com a fila e as em rota no service.
Falta uma regra que ligue o resíduo ao estado da solicitação dele.

## Decisão

> Vamos dar ao resíduo um status próprio, o enum `StatusResiduo`, e só deixar pedir a retirada
> de um resíduo `DISPONIVEL`, porque um objeto só pode ser retirado uma vez.

| Valor | Quando | Aparece na lista para descarte? |
| --- | --- | --- |
| `DISPONIVEL` | Resíduo recém-cadastrado, ou cuja solicitação foi Cancelada | Sim |
| `EM_SOLICITACAO` | Tem uma solicitação Pendente ou Em rota | Não |
| `DESCARTADO` | A solicitação foi Concluída | Não |

**Como o status muda**

| Ação na solicitação | Status do resíduo |
| --- | --- |
| Criar (só se o resíduo estiver `DISPONIVEL`) | `DISPONIVEL` para `EM_SOLICITACAO` |
| Iniciar rota | Continua `EM_SOLICITACAO` |
| Cancelar (pelo usuário ou pelo gerente) | Volta para `DISPONIVEL` |
| Finalizar | `EM_SOLICITACAO` para `DESCARTADO` |

- O resíduo nasce `DISPONIVEL`, e o status não é informado pelo usuário no cadastro nem na
  edição.
- A checagem fica no service de solicitação, antes de salvar a nova solicitação. Se o resíduo
  não estiver `DISPONIVEL`, o service lança uma exceção com mensagem clara.
- O mesmo método do service que muda o status da solicitação muda o status do resíduo, para os
  dois nunca ficarem diferentes.
- A tela de solicitar descarte lista só os resíduos `DISPONIVEL` do usuário. Agora o filtro é
  feito em Java sobre a lista do repository; quando o banco entrar (ADR-065), vira uma consulta
  com `WHERE status = 'DISPONIVEL'`. A lista "Meus resíduos" continua mostrando todos, com o
  status de cada um.
- Esconder da lista não substitui a checagem no service: a regra vale mesmo se alguém chamar
  o service direto, sem passar pela tela.

## Alternativas consideradas

### Alternativa 1: Um campo boolean no resíduo (por exemplo, `solicitado`)

- **Prós:** o mais simples de escrever; também funciona com `WHERE`.
- **Contras:** só tem dois estados. "Está na fila agora" e "já foi descartado" ficam iguais,
  e a tela "Meus resíduos" não consegue mostrar a diferença.
- **Por que não foi escolhida:** o enum custa quase o mesmo e diz o estado real do resíduo.

### Alternativa 2: Não guardar nada no resíduo e olhar as solicitações dele

- **Prós:** a informação mora num lugar só, no status da solicitação.
- **Contras:** para montar a lista de descarte, precisa buscar as solicitações de cada resíduo;
  no banco vira uma consulta com junção, mais difícil de explicar.
- **Por que não foi escolhida:** o grupo prefere um filtro direto no resíduo.

### Alternativa 3: Só esconder o resíduo da lista, sem validar no service

- **Prós:** muda uma parte só do código.
- **Contras:** a regra fica só na interface; qualquer outro caminho até o service cria a
  solicitação repetida.
- **Por que não foi escolhida:** regra de negócio precisa ficar na camada de negócio.

## Consequências

### Positivas

- A fila não recebe pedidos repetidos para o mesmo objeto.
- A lista de descarte vira um filtro simples por status, em Java agora e com `WHERE` depois.
- Um resíduo de uma solicitação cancelada volta a poder ser pedido, sem precisar ser
  cadastrado de novo.
- "Meus resíduos" pode mostrar se cada resíduo está disponível, na fila ou descartado.

### Negativas

- O estado fica em dois lugares (resíduo e solicitação). Se algum método mudar um e esquecer o
  outro, eles ficam diferentes.

### Neutras

- Nova regra de negócio RN13 em `docs/Requisitos.md`.
- Novo enum `StatusResiduo` e novo campo `status` em `Residuo`, salvo junto com os outros
  dados (JSON agora, coluna no banco depois).
- Resíduos já salvos em JSON sem o campo precisam ser lidos como `DISPONIVEL`.

## Riscos e pendências

- [ ] Se uma solicitação passar a aceitar vários resíduos, a checagem precisa olhar cada
  resíduo da lista, e não só um.
- [ ] Testar cada caminho: criar, cancelar pelo usuário, cancelar pelo gerente e finalizar,
  conferindo o status do resíduo depois de cada um.
- [ ] Quando o banco entrar (ADR-065), criar a coluna `status` na tabela de resíduos.
