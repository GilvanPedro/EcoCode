# ADR-090: Fazer a sessão de 30 dias com um token aleatório e a opção "manter conectado"

- **Status:** Aceita
- **Data:** 2026-11-28
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

O ADR-054 decidiu que a sessão vale 30 dias (RN06), mas a implementação não tinha sido feita:
o que existia era o "lembrar login" do ADR-047, que gravava o CPF de quem entrou e uma data
num `sessao.json`. Desde então muita coisa mudou. O usuário passou a ser identificado por
`UUID` (ADR-061), e o front já tem na tela de login a opção "Manter conectado por 30 dias".
Guardar o CPF num arquivo também era ruim: quem abrisse o arquivo via o CPF, e quem
escrevesse outro CPF nele entrava como outra pessoa.

## Decisão

> Vamos representar a sessão por uma entidade `Sessao` com um token aleatório, o `UUID` do
> usuário e a data de expiração (30 dias depois do login), e só criá-la quando a pessoa
> escolher "manter conectado", porque o token não revela nada sobre o usuário, não dá para
> adivinhar, e o comportamento fica igual ao da tela de login do front.

**A entidade (`Domain/Entities/Sessao`)**

| Campo | O que é |
| --- | --- |
| `token` | `UUID.randomUUID().toString()`, gerado ao criar a sessão |
| `usuarioId` | O `UUID` de quem entrou |
| `expiraEm` | `LocalDateTime.now().plusDays(30)` (`DIAS_VALIDADE = 30`) |

- `estaVencida()` responde se a data de agora já passou da `expiraEm`.

**O service (`Service/SessaoService`)**

| Método | O que faz |
| --- | --- |
| `criar(usuarioId)` | Encerra a sessão anterior deste computador, se houver, cria uma nova e guarda |
| `buscarValida()` | Lê o token guardado, procura a sessão e devolve só se não estiver vencida. Se estiver, encerra e devolve `null` |
| `encerrar()` | Apaga a sessão e o token guardado (é o "Sair") |

**Na tela do terminal**

- Ao abrir, a `TelaUsuarioTerminal` chama `buscarValida()`. Se houver sessão, busca o usuário
  pelo `UUID` e entra direto no menu.
- Se o usuário da sessão foi apagado, a sessão é encerrada e o login é pedido.
- Depois de um login com senha, a tela pergunta "Manter conectado por 30 dias? (s/n)". Só com
  "s" a sessão é criada.
- A opção "Sair" do menu chama `encerrar()`.

A primeira versão guardava a sessão no `sessao.json`. O ADR-091 trocou isso pela tabela
`sessoes` no banco e um `token.txt` no computador.

## Alternativas consideradas

### Alternativa 1: Continuar com o CPF no arquivo (ADR-047)

- **Prós:** já estava pronto.
- **Contras:** expõe o CPF e deixa entrar como outra pessoa trocando o arquivo.
- **Por que não foi escolhida:** o token aleatório resolve os dois problemas.

### Alternativa 2: Criar a sessão sempre, sem perguntar

- **Prós:** um passo a menos no login.
- **Contras:** num computador compartilhado, a próxima pessoa entra na conta de quem usou
  antes.
- **Por que não foi escolhida:** a tela de login do front já tem a caixa "manter conectado", e o
  terminal deve se comportar igual.

### Alternativa 3: Token JWT

- **Prós:** é o padrão em APIs web, e o próprio token carrega a validade.
- **Contras:** biblioteca nova, chave de assinatura, e mais conteúdo para estudar.
- **Por que não foi escolhida:** um token aleatório guardado no banco resolve o mesmo problema
  num programa deste tamanho.

## Consequências

### Positivas

- O RN06 está implementado: depois de 30 dias, o login é pedido de novo.
- O token não tem dado pessoal, e o usuário é sempre buscado de novo pelo `UUID`, com o cargo
  atualizado.

### Negativas

- Quem copiar o token entra como aquela pessoa até a sessão vencer ou ela sair.
- Uma sessão vencida só é apagada quando alguém tenta usá-la. Sessões abandonadas ficam
  guardadas.

### Neutras

- `SessaoService` entrou no `Instanciador` e é passado para as telas pelo construtor
  (ADR-058).
