# ADR-047: Lembrar o login entre execuções com um arquivo de sessão

- **Status:** Aceita
- **Data:** 2026-11-05
- **Autores:** Grupo do projeto

## Contexto

Com o login (ADR-043), toda vez que o programa abria era preciso digitar e-mail e senha de
novo. O grupo quis que o sistema "lembrasse" quem entrou, como o "lembrar de mim" de um site:
ao abrir, se a pessoa já tinha feito login, entra direto no menu.

## Decisão

> Vamos gravar, depois de um login bem-sucedido, um arquivo `sessao.json` com o CPF de quem
> entrou e uma data de validade, e ler esse arquivo ao iniciar o sistema.

**O arquivo**

```json
{
  "cpf": "52998224725",
  "expiraEm": "2026-11-12"
}
```

- Guarda o **CPF**, que não muda numa edição e é a chave do usuário (ADR-022), e **nunca a
  senha**.
- A sessão vale 7 dias (`DIAS_DE_VALIDADE`). Depois disso, o arquivo é apagado e o login é
  pedido de novo.
- A data é gravada como texto (`2026-11-12`), para não precisar de adaptador de `LocalDate`
  no Gson.
- O caminho fica em `Constantes.SESSAO_PATH` (`arquivos/sessao.json`), que o `.gitignore`
  já ignora.

**Quem faz o quê**

| Classe | Responsabilidade |
| --- | --- |
| `Util/Sessao` | Lê, grava e apaga o `sessao.json`. Arquivo inexistente, vencido ou estragado é tratado como "sem sessão" |
| `Util/LogarUsuario.logarUsuario` | Depois de passar em todas as verificações, chama `sessao.salvar(usuario)` |
| `Util/LogarUsuario.usuarioDaSessao` | Lê o CPF da sessão e **busca o usuário de novo** no service; se ele não existir mais, apaga a sessão e devolve `null` |
| `Util/LogarUsuario.deslogar` | Apaga a sessão |
| `TelaTerminal/TelaUsuarioTerminal` | Chama `usuarioDaSessao()`; só mostra o login se ele devolver `null` |
| `TelaTerminal/TelaCadastroResiduoTerminal` | Recebe o `LogarUsuario` no construtor e ganha a opção "0 - Sair da conta" |

- A `Sessao` só é usada pelo `LogarUsuario`. As telas não sabem que existe um arquivo: só
  perguntam se já tem alguém logado.
- O `sessao.salvar` é a última linha antes do `return` no login. Se qualquer verificação
  falhar antes, a exceção sai do método e o arquivo não é gravado.
- O usuário é buscado de novo, e não montado só com o que está no arquivo, porque o gerente
  pode ter removido a pessoa ou trocado o cargo dela depois do último login.

**No menu**

| Opção | Efeito |
| --- | --- |
| 7 - Sair | Fecha o programa e continua logado |
| 0 - Sair da conta | Apaga a sessão e fecha o programa; no próximo início é pedido o login |

## Alternativas consideradas

### Alternativa 1: Guardar e-mail e senha no arquivo e refazer o login ao abrir

- **Prós:** reaproveitaria o `logarUsuario` sem mudança.
- **Contras:** a senha ficaria escrita num arquivo, fácil de ler.
- **Por que não foi escolhida:** nenhum dado de senha deve sair do cadastro.

### Alternativa 2: Guardar o usuário inteiro no arquivo

- **Prós:** não precisaria buscar o usuário ao abrir.
- **Contras:** os dados ficariam desatualizados se o usuário fosse editado ou removido, e a
  senha cifrada iria junto.
- **Por que não foi escolhida:** só a chave basta; o resto vem do cadastro atualizado.

### Alternativa 3: Gravar a sessão na tela de login

- **Prós:** o `LogarUsuario` ficaria igual.
- **Contras:** a tela passaria a conhecer o arquivo, e qualquer outro lugar que fizesse login
  teria que lembrar de gravar.
- **Por que não foi escolhida:** gravar a sessão faz parte de fazer login; fica no mesmo
  método.

### Alternativa 4: Sessão sem validade

- **Prós:** nunca mais pediria login.
- **Contras:** um login esquecido valeria para sempre.
- **Por que não foi escolhida:** a validade limita o estrago de uma sessão esquecida aberta.

## Consequências

### Positivas

- Ao abrir o sistema, quem já fez login entra direto, com "Bem-vindo(a) de volta".
- Um usuário removido ou um arquivo estragado não deixam ninguém entrar; o sistema volta a
  pedir login.

### Negativas

- Qualquer pessoa que abra o programa no mesmo computador entra como quem ficou logado.
- Quem editar o `sessao.json` à mão pode trocar o CPF e entrar como outra pessoa, sem senha.
  Serve para um sistema de terminal local, não para um sistema em rede.
- O arquivo guarda uma sessão só: se outra pessoa fizer login, a anterior é substituída.

### Neutras

- No Spring (ADR-038), esse mecanismo não serve: o servidor atende várias pessoas ao mesmo
  tempo, e um arquivo único guardaria só quem entrou por último. Lá, o login vai devolver um
  *token* gerado pelo servidor, guardado no navegador de cada um.

## Riscos e pendências

- [ ] No Spring, trocar o arquivo de sessão por token (ou sessão HTTP) e não chamar o
  `sessao.salvar` no login do servidor.
- [ ] Avaliar perguntar "Lembrar login? (s/n)" em vez de lembrar sempre.
