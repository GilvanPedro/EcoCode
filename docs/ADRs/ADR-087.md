# ADR-087: Modelar o banco EcoCode em seis tabelas ligadas por chaves estrangeiras

- **Status:** Aceita
- **Data:** 2026-11-28
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

Para trocar o JSON pelo MySQL (ADR-085), o grupo precisou desenhar as tabelas. As entidades
já existiam (`Usuario`, `Residuo`, `Solicitacao`, `PontoColeta`, `RegistroLog`, `Sessao`),
todas identificadas por `UUID` (ADR-061), com enums para cargo, tipo, status, bairro e ação
do log. Algumas decisões tinham que ser tomadas na hora: como guardar o `UUID`, como guardar
data e hora, o que fazer com o nome de quem aparece no log e se a solicitação guarda o ponto
de coleta.

## Decisão

> Vamos criar o banco `EcoCode` com seis tabelas (`usuarios`, `residuos`, `solicitacoes`,
> `ponto_coleta`, `logs_auditoria` e `sessoes`), ligadas por chaves estrangeiras, com os enums
> guardados pelo nome e conferidos por `CHECK`, porque assim o próprio banco recusa dado
> inválido ou órfão, e as tabelas espelham as entidades que o grupo já conhece.

**As tabelas**

| Tabela | Colunas | Liga com |
| --- | --- | --- |
| `usuarios` | `id`, `nome_completo`, `cpf`, `email`, `senha_criptografada`, `cargo`, `data_nascimento`, `bairro` | |
| `residuos` | `id`, `id_usuario`, `codigo`, `tipo_residuo`, `quantidade`, `descricao`, `status` | `id_usuario` → `usuarios` |
| `solicitacoes` | `id`, `id_usuario`, `id_residuo`, `status`, `data_solicitacao` | `id_usuario` → `usuarios`, `id_residuo` → `residuos` |
| `ponto_coleta` | `id`, `nome`, `endereco`, `bairro` | |
| `logs_auditoria` | `id`, `id_usuario`, `acao_log`, `alvo`, `data_registro` | `id_usuario` → `usuarios` |
| `sessoes` | `token`, `id_usuario`, `expiracao` | `id_usuario` → `usuarios` |

```text
usuarios ──< residuos ──< solicitacoes
   │  └──────────────────────┘
   ├──< logs_auditoria
   └──< sessoes

ponto_coleta (sozinha)
```

**Regras que valem para todas**

- **`UUID` em `VARCHAR(36)`.** O id é gerado pelo Java (ADR-061) e gravado como texto, no
  formato `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`. Na leitura, `UUID.fromString` volta ao objeto.
- **Chaves estrangeiras com o prefixo `id_`** (`id_usuario`, `id_residuo`). O banco não deixa
  gravar um resíduo de um usuário que não existe.
- **Enums pelo nome** (`GERENTE`, `EM_ROTA`, `SETOR_BUENO`...), com `CHECK` listando os valores
  aceitos. Na leitura, `CargoUsuario.valueOf(...)` e os outros `valueOf` voltam ao enum.
- **Data e hora em `DATETIME`** (`data_solicitacao`, `data_registro`, `expiracao`), lidas com
  `getTimestamp(...).toLocalDateTime()`. A data de nascimento é `DATE`, e o Java continua
  mostrando `DD/MM/AAAA` (ADR-029).
- **O nome não é `UNIQUE`.** Duas pessoas podem se chamar "Maria Souza". O que identifica a
  pessoa é o `id`, e CPF e e-mail repetidos continuam barrados no service (ADR-057).

**Duas escolhas de modelagem**

- **O log guarda só o `id_usuario`, e o nome vem por `JOIN`.** O `RegistroLog` tem o nome de
  quem fez a ação, mas a tabela não. A `PersistenciaBancoLog` busca com
  `SELECT l.*, u.nome_completo FROM logs_auditoria l JOIN usuarios u ON u.id = l.id_usuario`.
  O nome fica num lugar só (normalização): se a pessoa mudar o nome, o log mostra o novo.
- **A solicitação não guarda o ponto de coleta.** O ponto mais próximo é calculado na hora pelo
  bairro do usuário (ADR-077), e o coletor vai buscar o resíduo. Guardar o ponto seria repetir
  uma informação que pode ser calculada.

## Alternativas consideradas

### Alternativa 1: Guardar o UUID em `BINARY(16)`

- **Prós:** ocupa menos espaço e o índice fica menor.
- **Contras:** no MySQL Workbench aparece como bytes ilegíveis, e precisa converter na ida e na
  volta.
- **Por que não foi escolhida:** com poucos dados o espaço não importa, e poder ler o id na
  tela ajuda a testar e a apresentar.

### Alternativa 2: Repetir o nome do usuário no log

- **Prós:** o `SELECT` do log fica sem `JOIN`.
- **Contras:** o nome ficaria em dois lugares e poderia ficar diferente.
- **Por que não foi escolhida:** o `JOIN` é simples e mostra normalização no relatório.

### Alternativa 3: Tabelas separadas para os enums (cargo, tipo, status)

- **Prós:** dá para mudar a lista de valores sem mexer na estrutura.
- **Contras:** mais tabelas e mais `JOIN` para valores que quase nunca mudam e já estão no
  código.
- **Por que não foi escolhida:** o `CHECK` resolve com bem menos trabalho.

## Consequências

### Positivas

- O banco recusa sozinho resíduo sem dono, solicitação de resíduo inexistente e status
  inventado.
- As tabelas têm o mesmo nome dos campos das entidades, o que facilita explicar o
  `linhaParaX` e o `preencher` de cada classe.

### Negativas

- Se um enum ganhar valor novo no Java (uma `AcaoLog` nova, por exemplo), o `CHECK` da tabela
  também precisa mudar, ou a gravação falha.
- As chaves estrangeiras impedem apagar um usuário que tem resíduos, solicitações, log ou
  sessão. Isso conversa com o RN07 (log não pode ser apagado), mas a remoção de usuário vai
  precisar de uma regra.
- Os nomes de tabela não seguem um padrão só: `ponto_coleta` está no singular e as outras no
  plural.

### Neutras

- As tabelas de bairros e arestas do grafo ficaram para depois (ADR-092).
- A sessão ganhou tabela própria (ADR-091).

## Riscos e pendências

- [ ] Guardar o script SQL de criação do banco no repositório (por exemplo, em
  `docs/banco/EcoCode.sql`), para quem clonar conseguir montar o banco igual.
- [ ] Se a FK de `solicitacoes.id_residuo` não tiver `ON DELETE CASCADE`, excluir um resíduo
  que já teve uma solicitação cancelada dá erro no banco. Testar esse caso.
- [ ] Decidir o que acontece ao remover um usuário com registros: bloquear com mensagem clara,
  ou marcar o usuário como inativo em vez de apagar.
- [ ] Atualizar o diagrama do banco no relatório (`docs/Diagramas.md`).
