# ADR-049: Usar uma árvore AVL em memória como índice das buscas, com o banco como fonte dos dados

- **Status:** Aceita
- **Data:** 2026-11-23
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

O projeto integrador pede uso de estruturas de dados estudadas no semestre, e o sistema
precisa responder rápido às buscas (RNF04). Até aqui, os dados ficavam num `Map` em memória e
eram gravados em JSON (ADR-011, ADR-024, ADR-026). Com o banco de dados entrando no projeto
(ADR-065), era preciso decidir qual o papel de uma estrutura em memória.

## Decisão

> Vamos manter uma árvore AVL em memória como índice (uma espécie de cache) das buscas, e o
> banco de dados como o lugar onde os dados realmente ficam.

| Momento | O que acontece |
| --- | --- |
| Ao iniciar o sistema | A árvore é montada com os registros lidos do banco |
| Ao cadastrar ou alterar | Grava **primeiro no banco**; só se der certo, atualiza a árvore |
| Ao buscar | A busca é feita **só na árvore**, sem ir ao banco |

- A AVL é uma árvore binária de busca que se rebalanceia a cada inserção ou remoção. Assim a
  altura fica sempre pequena, e a busca leva no máximo cerca de log₂(n) comparações.
- Gravar primeiro no banco garante que a árvore nunca tenha algo que o banco não tem. Se o
  banco falhar, a árvore não muda.

## Alternativas consideradas

### Alternativa 1: Buscar sempre direto no banco

- **Prós:** nenhuma estrutura extra para manter igual ao banco.
- **Contras:** não usa as estruturas da disciplina.
- **Por que não foi escolhida:** o trabalho pede a aplicação das estruturas estudadas.

### Alternativa 2: Árvore binária de busca comum (sem balanceamento)

- **Prós:** mais fácil de implementar.
- **Contras:** se os dados entrarem em ordem, a árvore vira uma lista e a busca fica lenta.
- **Por que não foi escolhida:** a AVL garante o desempenho em qualquer ordem de inserção.

### Alternativa 3: Usar a árvore como armazenamento principal

- **Prós:** dispensaria o banco.
- **Contras:** os dados sumiriam ao fechar o programa.
- **Por que não foi escolhida:** a árvore é só índice; quem guarda é o banco.

## Consequências

### Positivas

- Buscas rápidas, com uma estrutura que dá para mostrar e explicar na apresentação.
- A ordem "banco primeiro, árvore depois" evita dados que só existem na memória.

### Negativas

- A memória precisa caber todos os registros indexados.
- Toda alteração mexe em dois lugares; esquecer de atualizar a árvore deixa a busca
  desatualizada.
- A montagem ao iniciar deixa a abertura do sistema um pouco mais lenta.

## Riscos e pendências

- [ ] Definir quais dados terão AVL (usuários, resíduos, pontos de coleta) e qual a chave de
  cada árvore.
- [ ] Implementar as rotações (simples e duplas) e testar com inserções em ordem.
