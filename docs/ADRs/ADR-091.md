# ADR-091: Guardar a sessão no banco e só o token no computador

- **Status:** Aceita
- **Data:** 2026-11-28
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

A sessão de 30 dias (ADR-090) nasceu guardada inteira no `sessao.json`. Com o banco
(ADR-085), o grupo quis tirar esse arquivo, mas a sessão tem uma diferença em relação aos
outros dados: ela é deste computador. Se fosse só para o banco, o programa não saberia, ao
abrir, qual das sessões é a sua. Alguma coisa precisa ficar na máquina da pessoa.

No site, o mesmo problema é resolvido com um cookie: o navegador guarda um código e o
servidor guarda a sessão.

## Decisão

> Vamos dividir a sessão em duas partes: a sessão em si (token, usuário e expiração) na tabela
> `sessoes` do banco, e só o token num arquivo `arquivos/token.txt` no computador, porque assim
> o banco decide se a sessão vale, o computador só guarda a "chave" dela, e no site o
> `token.txt` vira um cookie sem mudar o resto.

| Parte | Onde fica | Classe | O que guarda |
| --- | --- | --- | --- |
| Sessão | Tabela `sessoes` | `Persistency/Banco/PersistenciaBancoSessao` | `token`, `id_usuario`, `expiracao` |
| Token local | `arquivos/token.txt` | `Util/TokenLocal` | Só o texto do token |

**`PersistenciaBancoSessao`**

- `salvar(sessao)` faz um `INSERT`, `buscar(token)` faz `SELECT ... WHERE token = ?`, e
  `apagar(token)` faz o `DELETE`.
- Não implementa `Persistencia<T>`: a sessão não é carregada inteira para a memória, é buscada
  pelo token quando precisa.

**`TokenLocal`**

- `guardar(token)` cria a pasta `arquivos/` se precisar e escreve o token.
- `ler()` devolve o token, ou `null` se o arquivo não existir.
- `apagar()` apaga o arquivo.

**O caminho de cada ação**

```text
Login com "manter conectado"  → apaga a sessão antiga → INSERT em sessoes → grava token.txt
Abrir o programa              → lê token.txt → SELECT em sessoes → confere a expiração
Sessão vencida ou não achada  → DELETE em sessoes → apaga token.txt → pede login
Sair                          → DELETE em sessoes → apaga token.txt
```

**No site (etapa do Spring)**

- O `token.txt` vira um cookie (por exemplo, `ECOCODE_TOKEN`), com `HttpOnly` e validade de
  30 dias. A tabela `sessoes` e o `SessaoService` continuam iguais; muda só a classe que lê e
  grava o token.

## Alternativas consideradas

### Alternativa 1: Continuar com o `sessao.json` inteiro

- **Prós:** nada para mudar.
- **Contras:** a validade ficaria fora do banco, e quem mexesse no arquivo poderia trocar a data
  de expiração.
- **Por que não foi escolhida:** com a expiração no banco, mexer no computador não estende a
  sessão.

### Alternativa 2: Só o banco, sem nada no computador

- **Prós:** nenhum arquivo.
- **Contras:** o programa não saberia de quem é a sessão ao abrir.
- **Por que não foi escolhida:** não funciona. Algo precisa identificar este computador.

### Alternativa 3: Sessão HTTP do Spring (`HttpSession`)

- **Prós:** pronta no Spring.
- **Contras:** só existe no site, não no terminal, e por padrão some quando o servidor reinicia.
- **Por que não foi escolhida:** o terminal precisa funcionar agora, e a mesma solução serve
  para o site depois.

## Consequências

### Positivas

- A validade fica no banco, onde o usuário não mexe.
- "Sair" apaga a sessão no banco, então um token copiado antes deixa de valer.
- A passagem para o site é trocar o `TokenLocal` por um cookie.

### Negativas

- O `token.txt` fica em texto puro na pasta `arquivos/`. Quem tiver acesso ao computador
  copia o token e entra.
- Cada computador tem uma sessão só. Entrar com outra conta no mesmo computador encerra a
  anterior.

### Neutras

- A pasta `arquivos/`, que não vai para o Git, agora guarda só o `token.txt` (os JSON eram do
  plano B).
- A tabela `sessoes` tem FK para `usuarios` (ADR-087).

## Riscos e pendências

- [ ] Apagar de tempos em tempos as sessões vencidas que ninguém usou
  (`DELETE FROM sessoes WHERE expiracao < NOW()`).
- [ ] No Spring, criar o cookie com `HttpOnly` e `Secure`.
