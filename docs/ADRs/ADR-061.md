# ADR-061: Identificar Usuario, Residuo e Solicitacao por um UUID gerado pelo próprio sistema

- **Status:** Aceita
- **Data:** 2026-11-24
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

Até aqui, cada entidade usava um dado de negócio como chave: o código para o resíduo
(ADR-011) e o CPF para o usuário (ADR-022). A nova entidade `Solicitacao` (ADR-063) precisa
apontar para um usuário e para um resíduo, e com o banco chegando (ADR-065), as tabelas vão
se ligar por chave. O ADR-042 tinha pensado num `id` gerado pelo banco.

## Decisão

> Vamos dar a `Usuario`, `Residuo` e `Solicitacao` um identificador `UUID`, gerado pelo
> próprio sistema no momento da criação, e usar esse id como chave.

| Entidade | Chave | Dado de negócio |
| --- | --- | --- |
| `Usuario` | `UUID id` | CPF e e-mail continuam únicos (ADR-057) |
| `Residuo` | `UUID id` | O **código** vira um campo único, não mais a chave |
| `Solicitacao` | `UUID id` | Guarda `usuarioId` e `residuoId` |

- O `UUID` é um número aleatório de 128 bits (`UUID.randomUUID()`), na prática impossível de
  repetir. Por ser gerado no app, o objeto já nasce com id, antes de ir para o banco ou para o
  JSON.
- As buscas por id de usuário e de resíduo ficam para depois: por enquanto, as buscas continuam
  por CPF, e-mail e código.

## Alternativas consideradas

### Alternativa 1: Manter CPF e código como chave

- **Prós:** nenhuma mudança.
- **Contras:** a solicitação teria que guardar o CPF e o código; se um deles mudar, as ligações
  quebram. A `Solicitacao` não tem um dado de negócio para ser chave.
- **Por que não foi escolhida:** um id próprio não muda e não depende das regras de negócio.

### Alternativa 2: `id` numérico gerado pelo banco (ADR-042)

- **Prós:** número pequeno e em ordem.
- **Contras:** o objeto só ganha id depois de gravado; antes disso, a solicitação não tem como
  apontar para ele. Não funciona enquanto o projeto ainda grava em JSON.
- **Por que não foi escolhida:** o UUID funciona igual com JSON e com banco.

## Consequências

### Positivas

- As três entidades seguem o mesmo padrão de chave.
- O CPF e o código podem ser corrigidos sem quebrar ligações.

### Negativas

- O UUID é longo e ruim de digitar; por isso o usuário continua buscando por CPF e código.
- Os registros já salvos sem id precisam ganhar um id ao ser carregados, ou ser recriados.

## Riscos e pendências

- [ ] Criar as buscas por id de usuário e de resíduo.
- [ ] Garantir a unicidade do código do resíduo no service.
