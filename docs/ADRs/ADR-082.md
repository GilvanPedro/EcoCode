# ADR-082: Ligar cada resíduo ao seu dono e só deixar o dono alterá-lo

- **Status:** Aceita
- **Data:** 2026-11-27
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

Até aqui, o resíduo não sabia de quem era. Qualquer usuário logado podia editar ou excluir o
resíduo de outra pessoa, e podia até pedir o descarte de um resíduo que não era dele. A tela
"Meus resíduos" do protótipo também não tinha como mostrar só os resíduos de quem está
logado.

## Decisão

> Vamos guardar no `Residuo` o id do dono (`usuarioId`, `final`) e só deixar o dono editar,
> excluir ou pedir o descarte do resíduo, porque o resíduo é um bem da pessoa.

- O `usuarioId` é preenchido no cadastro e nunca muda.
- `salvar`, `editar` e `excluir` do `GerenciarResiduosService` recebem o `Usuario`, e não um
  id solto.
- `editar` e `excluir` passam por `exigirDonoEDisponivel`:
  - quem não é o dono recebe `AcessoNegadoException`;
  - resíduo `EM_SOLICITACAO` ou `DESCARTADO` não pode ser alterado (`IllegalArgumentException`).
    Assim o funcionário nunca chega para buscar algo que mudou ou sumiu (ADR-071).
- `solicitar` no `GerenciarSolicitacoesService` lança `AcessoNegadoException` se o resíduo for
  de outra pessoa.
- Novos métodos: `listarDoUsuario(usuarioId)` e `listarDisponiveisDoUsuario(usuarioId)`, este
  para a tela de solicitar descarte.
- **Na tela:** o gerente vê todos os resíduos; os outros cargos veem só os seus.

## Alternativas consideradas

### Alternativa 1: Deixar o gerente editar e excluir qualquer resíduo

- **Prós:** o gerente corrige erros de cadastro.
- **Contras:** o gerente mexeria num bem que não é dele, sem o dono saber.
- **Por que não foi escolhida:** o gerente só vê; quem corrige é o dono.

### Alternativa 2: Guardar o objeto `Usuario` inteiro dentro do resíduo

- **Prós:** acesso direto aos dados do dono.
- **Contras:** o JSON duplicaria os dados do usuário (inclusive a senha cifrada) em cada
  resíduo, e eles ficariam desatualizados.
- **Por que não foi escolhida:** o id basta e é o que vira chave estrangeira no banco.

## Consequências

### Positivas

- Cada usuário só mexe no que é seu, com a regra no service.
- A tela de solicitar mostra só o que o usuário pode de fato pedir.

### Negativas

- Resíduos antigos do JSON, cadastrados antes da mudança, ficam sem dono e sem `id`. Eles
  precisaram ser apagados e cadastrados de novo (ver o documento de testes).

### Neutras

- Na tabela de resíduos do banco, `usuario_id` vira chave estrangeira para usuários.

## Riscos e pendências

- [ ] Decidir o que acontece com os resíduos quando o gerente remove o usuário dono.
- [ ] Quando o banco entrar (ADR-065), criar a coluna `usuario_id`.
