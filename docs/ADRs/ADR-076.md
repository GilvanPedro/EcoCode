# ADR-076: Deixar só o gerente cadastrar, editar e excluir ponto de coleta

- **Status:** Aceita
- **Data:** 2026-11-26
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

O ADR-072 colocou os 5 ecopontos da Comurg no grafo, mas o sistema ainda não tinha uma forma
de guardar os pontos de coleta. Um ponto errado manda o usuário para o lugar errado, então
era preciso decidir quem pode mexer nesses dados e como a edição funciona.

## Decisão

> Vamos criar o módulo de pontos de coleta e deixar só o `GERENTE` cadastrar, editar e excluir
> um ponto, porque é um dado do sistema e não de cada usuário. Qualquer pessoa logada pode
> listar e buscar.

**Entidade `PontoColeta`**

| Campo | Regra |
| --- | --- |
| `id` | `UUID` gerado pelo sistema, `final` (ADR-061) |
| `nome` | Obrigatório, sem espaços nas pontas |
| `endereco` | Obrigatório |
| `bairro` | Obrigatório, do enum `Bairro`; é o vértice usado no Dijkstra |

- A validação fica na própria entidade, nos construtores e nos `set` (ADR-014).
- O `GerenciarPontoColetaRepository` guarda os pontos num `Map<UUID, PontoColeta>` e grava em
  `pontos_coletas.json`. Atualizar, remover ou buscar um id que não existe lança exceção.
- No `GerenciarPontoColetaService`, `cadastrar`, `editar` e `excluir` recebem quem está
  fazendo (`Usuario quem`) e chamam `exigirGerente`, que lança `AcessoNegadoException` para
  qualquer outro cargo.
- **Edição parcial:** campo nulo ou vazio mantém o valor atual, como na edição do usuário
  (ADR-060).
- Cada uma das três ações grava um registro no log de auditoria (ADR-080).

## Alternativas consideradas

### Alternativa 1: Deixar o funcionário também gerenciar pontos

- **Prós:** menos dependência do gerente.
- **Contras:** mais gente podendo mudar um dado que afeta todos os usuários.
- **Por que não foi escolhida:** o grupo decidiu que dado do sistema é com o gerente, como a
  promoção de cargo (ADR-053).

### Alternativa 2: Deixar os pontos fixos no código, como as arestas do grafo

- **Prós:** nenhum CRUD para fazer.
- **Contras:** abrir ou fechar um ecoponto exigiria mudar o código.
- **Por que não foi escolhida:** pontos de coleta mudam mais que os bairros.

## Consequências

### Positivas

- A regra de acesso fica no service, então vale para o terminal e para o front futuro.
- Editar só o que mudou evita redigitar nome e endereço.

### Negativas

- Não dá para "apagar" um campo pela edição, mas nenhum campo do ponto é opcional.

### Neutras

- Novos arquivos: `PontoColeta`, `GerenciarPontoColetaRepository`,
  `GerenciarPontoColetaService` e as interfaces dos dois.
- O bairro do ponto precisa existir no grafo; como vem do enum `Bairro`, sempre existe.

## Riscos e pendências

- [ ] Cadastrar os 5 ecopontos da Comurg pelo próprio sistema antes da apresentação.
- [ ] Decidir se excluir um ponto deve ser bloqueado quando ele for o único do sistema.
- [ ] Quando o banco entrar (ADR-065), criar a tabela de pontos de coleta.
