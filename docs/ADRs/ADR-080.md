# ADR-080: Montar o log de auditoria com o enum AcaoLog, o RegistroLog imutável e a pilha

- **Status:** Aceita
- **Data:** 2026-11-26
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

O ADR-052 definiu o log de auditoria: só recebe registros novos, guarda quem, quando, ação e
alvo, e é consultado como pilha. Com a `PilhaEncadeada<T>` pronta (ADR-079), faltava decidir
quais ações entram, como o registro é montado e quem pode ver.

## Decisão

> Vamos registrar só as ações importantes, listadas no enum `AcaoLog`, num `RegistroLog` com
> todos os campos `final`, guardado numa `PilhaEncadeada` no repository, e deixar só o
> gerente listar o log.

**As 10 ações do `AcaoLog`**

| Grupo | Ações |
| --- | --- |
| Usuários | `CADASTROU_USUARIO`, `EDITOU_USUARIO`, `PROMOVEU_USUARIO`, `REMOVEU_USUARIO` |
| Pontos de coleta | `CADASTROU_PONTO`, `EDITOU_PONTO`, `EXCLUIU_PONTO` |
| Solicitações | `PEGOU_SOLICITACAO`, `CONCLUIU_SOLICITACAO`, `CANCELOU_SOLICITACAO` |

Cada ação tem uma descrição em português para a tela (ex.: "Concluiu uma coleta").

**`RegistroLog`**

| Campo | Origem |
| --- | --- |
| `id` | `UUID` gerado no construtor |
| `usuarioId`, `nomeUsuario` | Quem fez a ação; o nome fica copiado, para continuar legível mesmo se o usuário for removido |
| `dataRegistro` | `LocalDateTime.now()` no construtor; ninguém informa a data |
| `acaoLog` | Valor do enum |
| `alvo` | Texto curto: CPF e cargo, nome do ponto, id da solicitação |

- Todos os campos são `final` e não há `set`: depois de criado, o registro não muda (RN07).
- `GerenciarLogService.registrar(quem, acao, alvo)` é chamado pelos outros services **depois**
  que a ação deu certo. A tela nunca grava log.
- `GerenciarLogService.listar(quem)` lança `AcessoNegadoException` se quem consulta não for
  `GERENTE`.
- O `GerenciarLogRepository` carrega o `log.json`, ordena pela data e empilha do mais antigo
  para o mais novo, para o mais novo ficar no topo. Ao gravar, salva em ordem cronológica.
- O repository não tem editar nem excluir.

**Quem registra o quê hoje**

| Service | Ações registradas |
| --- | --- |
| `GerenciarUsuariosService` | Cadastro pelo gerente, promoção, remoção |
| `GerenciarPontoColetaService` | Cadastrar, editar e excluir ponto |
| `GerenciarSolicitacoesService` | Pegar da fila, concluir, cancelar (só quando o gerente cancela) |

## Alternativas consideradas

### Alternativa 1: Registrar toda ação, inclusive as do usuário comum

- **Prós:** histórico completo.
- **Contras:** o log enche de cadastros de resíduo e logins, e o que importa se perde.
- **Por que não foi escolhida:** o log é para auditar quem tem poder no sistema.

### Alternativa 2: Ação como texto livre

- **Prós:** nenhum enum para manter.
- **Contras:** a mesma ação escrita de jeitos diferentes; impossível filtrar.
- **Por que não foi escolhida:** o enum padroniza e permite filtro por ação no futuro.

## Consequências

### Positivas

- O gerente vê primeiro o que acabou de acontecer.
- Um registro não pode ser alterado nem pelo código.

### Negativas

- `EDITOU_USUARIO` existe no enum, mas a edição de usuário ainda não grava log.
- O cancelamento feito pelo próprio usuário não é registrado (decisão de registrar só ações
  da equipe).

### Neutras

- Novo arquivo `arquivos/log.json`. O Gson precisa do adaptador de `LocalDateTime` (ADR-081).
- A lista final de ações ainda pode mudar depois da conversa do grupo.

## Riscos e pendências

- [ ] Decidir com o grupo se `EDITOU_USUARIO` passa a ser gravado no `editar`, ou sai do enum.
- [ ] Fechar a lista final do `AcaoLog`.
- [ ] Quando o banco entrar (ADR-065), a tabela `log` só recebe `INSERT` e `SELECT`.
