# ADR-088: Gravar com upsert, apagar os excluídos e só inserir no log

- **Status:** Aceita
- **Data:** 2026-11-28
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

A interface `Persistencia<T>` tem um `salvar(List<T>)` que recebe a lista inteira, porque foi
feita para o JSON: reescrever o arquivo todo era o jeito natural (ADR-085). No banco não dá
para "reescrever a tabela" do mesmo jeito. Para cada item da lista, o banco pode já ter a linha
(foi editado) ou não ter (é novo). E um item que sumiu da lista (foi excluído) continua no banco
se ninguém apagar.

## Decisão

> Vamos gravar cada item com um upsert (`INSERT ... ON DUPLICATE KEY UPDATE`), apagar antes as
> linhas que não estão mais na lista nas tabelas em que dá para excluir, e só inserir no log, com
> `INSERT IGNORE`, porque assim o `salvar(List<T>)` continua igual para o repository e cada
> tabela respeita a regra da sua entidade.

**Upsert**

```sql
INSERT INTO residuos (id, id_usuario, codigo, tipo_residuo, quantidade, descricao, status)
VALUES (?, ?, ?, ?, ?, ?, ?)
ON DUPLICATE KEY UPDATE quantidade = VALUES(quantidade),
                        descricao  = VALUES(descricao),
                        status     = VALUES(status)
```

- Se o `id` ainda não existe, insere. Se já existe, atualiza.
- O `UPDATE` só lista o que pode mudar. No resíduo, `id_usuario`, `codigo` e `tipo_residuo`
  ficam de fora, o que repete no banco a regra de não alterar tipo nem código (ADR-016). Na
  solicitação, só o `status` muda. No usuário, CPF e data de nascimento ficam de fora.
- Os itens vão em lote (`addBatch` e `executeBatch`), numa ida só ao banco.

**O que muda em cada tabela**

| Classe | Como grava | Apaga os excluídos? |
| --- | --- | --- |
| `PersistenciaBancoResiduo` | Upsert | Sim, `removerExcluidos` |
| `PersistenciaBancoPontoColeta` | Upsert | Sim, `removerExcluidos` |
| `PersistenciaBancoSolicitacao` | Upsert | Não: solicitação não é apagada, só cancelada |
| `PersistenciaBancoUsuario` | Upsert | Ainda não (pendência) |
| `PersistenciaBancoLog` | `INSERT IGNORE` | Não: o log não pode ser apagado (RN07) |

**`removerExcluidos`**

1. Monta um `Set` com os ids que estão na lista.
2. Faz `SELECT id` na tabela.
3. Cada id do banco que não está no `Set` vai para um `DELETE` em lote.
4. Depois disso, roda o upsert.

**`INSERT IGNORE` no log**

- O repository manda a pilha inteira a cada registro novo. Os registros antigos já estão no
  banco e dariam erro de chave repetida. Com o `IGNORE`, eles são pulados e só o novo entra.
- Não tem `UPDATE` nem `DELETE`: o que foi registrado não muda (ADR-052, RN07).

## Alternativas consideradas

### Alternativa 1: Apagar a tabela inteira e inserir tudo de novo

- **Prós:** é o mesmo raciocínio do JSON, e o código fica curto.
- **Contras:** com as chaves estrangeiras (ADR-087), apagar `usuarios` ou `residuos` quebra as
  outras tabelas. No log, apagar tudo vai contra o RN07.
- **Por que não foi escolhida:** não funciona com FK e é perigoso.

### Alternativa 2: Métodos separados `inserir`, `atualizar` e `apagar` na interface

- **Prós:** cada operação vira um SQL só, sem reler a tabela.
- **Contras:** muda a interface `Persistencia<T>`, todos os repositories e a
  `PersistenciaArquivo`.
- **Por que não foi escolhida:** a graça da troca era não mexer nos repositories. Fica como
  melhoria para depois.

## Consequências

### Positivas

- Os repositories continuam chamando só `salvar(listar())`.
- O banco protege campos que não podem mudar, mesmo se o Java tiver um erro.
- O log só cresce, como pede o RN07.

### Negativas

- Cada mudança regrava a lista inteira e, em resíduos e pontos, ainda faz um `SELECT` de todos
  os ids. Com milhares de registros isso fica lento.
- `ON DUPLICATE KEY` dispara com qualquer chave única da tabela, não só com o `id`. Se uma
  coluna como o e-mail for `UNIQUE` e o service deixar passar um repetido, o upsert atualiza a
  linha da outra pessoa em vez de dar erro. Hoje o service barra antes (ADR-057).
- Sem transação, um erro entre o `removerExcluidos` e o upsert deixa o banco pela metade.

### Neutras

- `VALUES(coluna)` dentro do `ON DUPLICATE KEY UPDATE` está marcado como antigo no MySQL 8,
  mas ainda funciona.

## Riscos e pendências

- [ ] Fazer o `removerExcluidos` no `PersistenciaBancoUsuario`. Hoje um usuário removido volta
  depois de reiniciar o programa (ver ADR-085 e ADR-087 sobre as FKs).
- [ ] Colocar o `removerExcluidos` e o upsert numa transação (`setAutoCommit(false)`,
  `commit`, `rollback`).
- [ ] Se o sistema crescer, trocar o "salvar tudo" por métodos de uma linha só (Alternativa 2).

## Referências

- ADR-016 (tipo e código não mudam), ADR-052 e ADR-080 (log), ADR-057 (duplicidade no service),
  ADR-085 (banco), ADR-087 (tabelas e FKs). RN07.
