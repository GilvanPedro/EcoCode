# ADR-085: Trocar os arquivos JSON pelo MySQL com JDBC, mantendo a interface Persistencia

- **Status:** Aceita
- **Data:** 2026-11-28
- **Autores:** Grupo do projeto (Gilvan Pedro, Sidney Emanuel, Guilherme Scarcela, João Paulo e Dários Suess)

## Contexto

Até aqui, cada repository guardava os dados em memória e gravava tudo num arquivo JSON a cada
mudança (ADR-024, ADR-026). O banco tinha sido adiado no ADR-042, e o ADR-065 já tinha
decidido que, quando entrasse, ele seria o único lugar dos dados. O PI pede persistência em
banco (RNF03), e o back-end em Java puro já estava completo e testado.

A camada de persistência já tinha uma interface pronta:

```java
public interface Persistencia<T> {
    List<T> carregar();
    void salvar(List<T> itens);
}
```

Os repositories só conhecem essa interface. Quem grava em arquivo é a `PersistenciaArquivo<T>`,
mas o repository não sabe disso. Esse detalhe abria caminho para trocar o arquivo pelo banco
sem mexer no resto do sistema.

## Decisão

> Vamos guardar os dados num banco MySQL, acessado com JDBC puro, criando uma classe
> `PersistenciaBancoX implements Persistencia<X>` para cada entidade, porque assim a troca
> acontece numa linha de cada repository e o service, o domínio e as estruturas não mudam.

- As classes novas ficam em `Persistency/Banco`:

| Classe | Entidade | Tabela |
| --- | --- | --- |
| `PersistenciaBancoUsuario` | `Usuario` | `usuarios` |
| `PersistenciaBancoResiduo` | `Residuo` | `residuos` |
| `PersistenciaBancoSolicitacao` | `Solicitacao` | `solicitacoes` |
| `PersistenciaBancoPontoColeta` | `PontoColeta` | `ponto_coleta` |
| `PersistenciaBancoLog` | `RegistroLog` | `logs_auditoria` |

- A troca em cada repository é uma linha só:

```java
// antes
private final Persistencia<Residuo> persistencia = new PersistenciaArquivo<>(Constantes.RESIDUOS_PATH, Residuo.class);
// depois
private final Persistencia<Residuo> persistencia = new PersistenciaBancoResiduo();
```

- Cada classe faz duas coisas: `carregar()` roda um `SELECT` e transforma cada linha num
  objeto (`linhaParaX`), e `salvar()` grava a lista inteira (`preencher` + `addBatch`). Como
  gravar está no ADR-088.
- Toda consulta usa `PreparedStatement` com `?`, nunca texto concatenado, para não abrir
  espaço para SQL injection.
- O repository continua com os dados em memória (o `Map`, a `ArvoreAVL` dos resíduos e a
  `PilhaEncadeada` do log). Ele carrega tudo do banco ao nascer e grava no banco a cada
  mudança. As estruturas são o índice das buscas e o banco é a fonte (ADR-049).
- A `PersistenciaArquivo<T>` continua no projeto como **plano B**: se o banco der problema
  perto da apresentação, basta voltar a linha de cada repository.
- Os `SQLException` viram `RuntimeException` com uma mensagem em português ("Erro ao carregar
  resíduos: ..."), para a interface `Persistencia` continuar sem `throws`.
- O driver é o `mysql-connector-j`, no `pom.xml`, com escopo `runtime`.

## Alternativas consideradas

### Alternativa 1: Spring Data JPA (Hibernate)

- **Prós:** quase não precisa escrever SQL, e o Spring já está no `pom.xml` (ADR-038).
- **Contras:** pede anotações nas entidades, repositories do Spring e um jeito novo de pensar
  os dados. O grupo ainda está aprendendo Spring.
- **Por que não foi escolhida:** mudaria a camada de repository inteira, e as estruturas
  próprias (AVL, pilha, fila) deixariam de ter papel. Com JDBC o grupo escreve e explica cada
  SQL.

### Alternativa 2: PostgreSQL, como na tentativa do ADR-042

- **Prós:** já tinha um começo de código.
- **Contras:** o grupo tem mais prática com MySQL, e é ele que está instalado nas máquinas.
- **Por que não foi escolhida:** escolha do grupo pela ferramenta que conhece.

### Alternativa 3: Trocar o repository inteiro por um que fala direto com o banco

- **Prós:** sem cópia dos dados em memória.
- **Contras:** cada busca viraria um `SELECT`, e a AVL e a pilha sairiam do sistema.
- **Por que não foi escolhida:** perde a parte de Estrutura de Dados, e a interface
  `Persistencia` já resolvia a troca com muito menos mudança.

## Consequências

### Positivas

- Os dados ficam num banco de verdade, que o grupo consegue abrir e consultar (RNF03).
- Service, domínio, telas e estruturas não mudaram. A interface `Persistencia<T>` provou o
  valor que tinha.
- Voltar para o JSON é trocar uma linha.

### Negativas

- Os dados ficam duas vezes: no banco e em memória. Se outra pessoa mexer no banco direto,
  o programa só vê a mudança quando reiniciar.
- `salvar()` grava a lista inteira a cada mudança. Com poucos dados não pesa, mas não escala.
- O sistema não sobe sem o MySQL rodando e sem o `.env` com os dados de acesso.

### Neutras

- Os arquivos `.json` de `arquivos/` deixam de ser usados (podem ser apagados). As constantes
  `*_PATH` continuam na `Constantes` por causa do plano B.
- O `PersistenciaArquivo` e o adaptador de `LocalDateTime` do Gson (ADR-081) continuam
  funcionando, só não são mais usados.

## Riscos e pendências

- [ ] **`PersistenciaBancoUsuario` não tem `removerExcluidos`.** O gerente remove um usuário,
  ele some da memória, mas o `salvar` só faz upsert e a linha continua no banco. Ao reiniciar,
  o usuário volta. Quando isso for feito, lembrar que as FKs de `residuos`, `solicitacoes` e
  `logs_auditoria` impedem apagar um usuário que já tem registros (ver ADR-087).
- [ ] As gravações não estão numa transação. Se a conexão cair no meio do `salvar`, parte da
  lista pode ficar gravada e parte não.
- [ ] Quando o Spring entrar, avaliar se as classes `PersistenciaBancoX` viram componentes do
  Spring ou continuam sendo criadas pelo `Instanciador`.

## Referências

- ADR-049 (AVL como índice, banco como fonte), ADR-086 (conexão), ADR-087 (tabelas),
  ADR-088 (como gravar). RNF03.
